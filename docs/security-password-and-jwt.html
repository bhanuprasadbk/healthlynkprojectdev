Password & JWT token security

This document summarizes how the Health Lynk application handles user passwords and JSON Web Tokens (JWTs), based on the current implementation. It is intended for stakeholders and security reviewers.

Password security (server & storage)

  • No plaintext storage. Passwords are never stored as readable text. The server stores a one-way password hash in the database using Werkzeug’s generate_password_hash / check_password_hash (industry-standard salted hashing; the raw password cannot be recovered from the stored value).
  • Verification at login. On sign-in, the server compares the submitted password to the stored hash with verify_password; if the user does not exist or the password does not match, the API responds with a generic error (invalid credentials) to avoid revealing whether a username is registered.
  • Minimum length on registration. New accounts must use a password of at least 8 characters (enforced on the registration API).
  • Inactive accounts. Users marked inactive cannot complete login even with a correct password (access is denied with a distinct forbidden response).
  • Transport. In production, the application should be served over HTTPS so passwords and tokens are encrypted in transit between the browser and the API. (TLS is a deployment/infrastructure responsibility.)

Operational recommendation: enforce a strong SECRET_KEY and database credentials in environment configuration; use a dedicated secret manager in production.

JWT access token security

  • Library. API authentication uses Flask-JWT-Extended, a widely used Flask extension for issuing and validating JWTs.
  • Signing secret. Tokens are signed with a dedicated JWT_SECRET_KEY supplied via environment configuration (must be set to a strong, random value in production; default placeholders in code are for development only).
  • Limited lifetime. Access tokens are configured with an expiry of 3,600 seconds (one hour) by default (JWT_ACCESS_TOKEN_EXPIRES). After expiry, the client must sign in again to obtain a new token (there is no refresh-token flow in the current codebase).
  • Claims embedded in the token. The token’s subject identity is the user’s id; an additional claim carries the user’s role for authorization decisions on the server.
  • Protected routes. Sensitive API endpoints require a valid JWT (@jwt_required()). Endpoints that need specific privileges use a role check that re-verifies the JWT and ensures the role claim is one of the allowed roles (for example admin, billing, caregiver, provider staff) before executing the handler.
  • Consistent error handling. JWT-related failures (missing, invalid, or expired token) are handled centrally and returned to the client as 401 Unauthorized with an appropriate message.
  • How the browser sends the token. The web client attaches the token as an Authorization: Bearer <token> header on API requests when a session exists.
  • Browser storage. After login, the access token and basic user profile fields are stored in localStorage under a fixed application key so the session survives page reloads. If the API reports an expired token (message matching “token has expired”), the client clears the session and the user signs in again.
  • CORS. Cross-origin access to API routes is restricted to origins configured in server settings (for example the front-end development URL or your deployed web origin), reducing exposure to arbitrary third-party sites calling the API from a browser.

Transparency for risk discussions: storing JWTs in localStorage is common for SPAs but means any cross-site scripting (XSS) vulnerability in the front end could theoretically expose the token. Mitigations include strict HTTPS, a strong Content Security Policy, dependency updates, and code review. Alternatives such as HTTP-only cookies involve different trade-offs (CSRF protections, cookie flags) if you ever want to harden the model further.

Quick summary for clients

  • Passwords: hashed before storage; minimum length enforced; login errors are generic.
  • JWTs: signed with a configurable secret; hourly expiry; role embedded for server-side checks; sent as Bearer tokens; CORS limited to configured front-end origins.
